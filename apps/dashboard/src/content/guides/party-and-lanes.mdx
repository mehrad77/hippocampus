A vault has two kinds of members. The **humans** it belongs to, listed in its config, outrank everyone. The **agents** that share it (the party, in the codex look) each have a sheet in `party/<id>.md` that says what the agent is for (its **lane**) and where its word counts as canon (its **authority domains**). The curator uses these sheets to settle conflicts. `onboard` uses them to tell each agent who it is, and `HANDBOOK.md` lists them for everyone.

Any type with the `actor` capability works this way; the vault's own `party` type has it.

## An agent's sheet

```markdown
---
type: party
title: Home Finder
aliases: []
tags: []
lane: "Housing: listing hunt, lease, and address documents."
authority: [housing]
host: any MCP client
---

## Notes
Owns [[apartment-hunt]].
```

| Property | Meaning |
| --- | --- |
| file name | The agent id, e.g. `home-finder`. Episodes, tokens and MCP connections use it |
| `title` | The display name |
| `lane` | One or two sentences: what this agent does, and what it stays out of |
| `authority` | Domains where its reports are canon at once |
| `host` | Where it runs, for your reference (a chat app, a bot, a coding agent) |

Agent ids are lowercase letters, digits and dashes, starting with a letter or digit, up to 63 characters. That's the same rule everywhere, so an id works on the command line, on the hosted app and in its consent page. The humans' ids and the reserved ids `human`, `curator`, `unknown` and `hippocampus` can't be agent ids, and an agent must use its exact id: a title or alias doesn't count.

## Domains and authority

Domains are the tags that define lanes. They're listed in `_hippo/config.yaml`:

```yaml
domains: [residency, insurance, university, language, housing, career, finance, health, story]
```

Add more whenever life grows a new area: on the Agents page under Areas (Domains), or with `hippo domain add <id…>`. Either one updates the config and the Handbook in one commit.

The rule is simple. **An agent has authority over a note when one of its `authority` domains matches one of the note's tags, or the note's type.** Matching ignores case. Authority is computed fresh for every decision. Retag a note or edit an agent's sheet, and the next report is judged by the new rules.

In the example vault:

| Agent | Authority | Canon at once on, for example |
| --- | --- | --- |
| `residency-agent` | residency, insurance | Migration Agency, the permit portal, the residence-permit goal |
| `campus-agent` | university, language | Harbor University, the HU Language Center, the student portal |
| `home-finder` | housing | The apartment-hunt goal |
| `job-scout` | career | The paid-work goal |
| `game-master` | story | The Lisbon arc |
| `archivist` | none | Nothing: all its reports start as rumors |

Notes with no matching tag, like Lisbon itself, belong to no one. Every report there is a rumor until enough agents agree. See <Link guide="facts-and-status">Facts and their status</Link>.

<Aside kind="warn" title="Types count as domains">

A domain is also compared with the note's **type**, and a type can give one of its fields a `domain` of its own. An agent with authority over a domain named `lore` would be authoritative on every lore note. Keep domain names distinct from type names unless that's what you want.

</Aside>

### New notes inherit a lane

When the curator creates a new entity from an episode, it tags it with domains from your list, as the model suggests. If the model suggests none, the note gets the **reporting agent's authority domains**. So a flat in Alfama that the home finder mentions first will usually end up tagged `housing`, with the home finder holding authority over it. Retag the note in Obsidian if that's wrong.

## Humans are not agents

The humans are listed under `humans:` in `_hippo/config.yaml`:

```yaml
humans:
  - { id: player, domains: [finance, housing], github: player-gh, gitlab: player-gl }
  - { id: partner, domains: [health] }
```

| Key | Meaning |
| --- | --- |
| `id` | The human's id. It can't be used as an agent id |
| `domains` | Where this human outranks the other humans. Leave it empty in a vault with one human |
| `github` | The GitHub login, so the hosted dashboard knows which human signed in |
| `gitlab` | The GitLab username, the same for a vault kept on GitLab (matched against the GitLab account you connected) |

The first one is the **primary** human: facts with no `by` are theirs, and the local dashboard acts as them unless you start it with `hippo dashboard --as <human>`. On the hosted app, the signed-in person maps to the human with their `github` login; on a GitLab vault, the human with their connected GitLab username as `gitlab` comes first. Otherwise it's the primary human. Setting up a vault fills these in for you.

### Sharing a vault (hosted app)

On the hosted app, a vault's owner shares it from **Setup → People → Invite someone**: by GitHub username (only they can accept, and they see the invite when they sign in) or as a link that works once. Each person joins as **a human of their own**, either one already in `humans:` or a new one added when they accept, with their login written onto it.

| Role | Can |
| --- | --- |
| Owner | Everything: invites and removes people, the repository, every key, curation |
| Member | Adds memories, settles disputes and approves agents as their own human; makes keys for their own agents |
| Viewer | Reads everything, changes nothing |

Someone you share with is never the primary human by accident: they act only as the human they were invited as. Removing them, or their leaving, revokes the keys they made and the apps they connected for that vault; their human and everything they wrote stay. An invite also lets a person into the hosted app without waiting for an admin.

A human's word outranks every agent everywhere, whatever the tags say. Between humans, the one with the domain wins, and two humans without it open a dispute; see <Link guide="precedence-and-disputes">Precedence and disputes</Link>. Facts written by a human's id and memories a human scribes count as theirs. Humans don't need a sheet in `party/`. Your own note in `characters/` (`characters/player.md` in the example) is about you as a person, not about permissions.

## Strangers at the table

An agent that writes to the inbox without a sheet in `party/` is **unknown**:

- Its episodes are accepted and consolidated. Nothing is thrown away.
- It has no authority anywhere, so everything it reports starts as a rumor.
- `onboard` tells it so, and asks it to **introduce** itself: a title, its lane, where it runs, its model and a few lines about what it does. The introduction waits in `inbox/<id>/` for you.
- On the Agents page (Party, in the codex look), **Approve** seats it with the authority domains you choose (you can change its name and lane first), and **Dismiss** tears the introduction up. A dismissed agent can still write, as a rumor, and may introduce itself again.
- The Home page lists unknown agents under what needs your attention, and Setup offers to add them.

An agent's id comes from the episode's `agent:` property, or else from its folder in `inbox/`. Over MCP it comes from the connection: `--agent`, `?agent=`, a single-agent key or connector on the hosted app, or the `agent` argument the agent passes with an agent key. Ids are compared in lowercase.

## Adding an agent

**From the dashboard.** The Agents page, and the Agents step of Setup, add a member with an id, a name, a lane, authority domains from your list, and a host. The dashboard checks the id, refuses unknown domains (add new ones under Areas (Domains) on the same page first), refuses a human's id or one that's already taken, then writes `party/<id>.md` and regenerates `HANDBOOK.md` together.

**By hand.** Copy `_hippo/templates/party.md` (Obsidian's template picker offers it) to `party/<id>.md` and fill in `lane`, `authority` and `host`. The next sleep, or `hippo handbook`, puts it in the handbook.

Then connect the agent with that id. See <Link guide="connecting-agents">Connecting agents</Link>.

<Aside kind="tip" title="Write lanes like job descriptions">

A good lane says what the agent owns *and* what it leaves alone: "Goal board and story framing. Records story beats; never steals other lanes." Agents read their lane in `onboard`, and a clear one keeps them from wandering into each other's work.

</Aside>

## Retiring an agent

The example's `archivist` is a fact-checker whose job Hippocampus took over: canon, `ask_canon` and disputes now do what it used to. Its sheet stays as a record, with no authority. To retire an agent, empty its `authority` and revoke its token if it has one. Its past facts keep their provenance.
